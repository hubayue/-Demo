# Godot 设计原型工程边界

## 决策

当前工程的目标不是上线运营，也不是复刻线上账号体系，而是把老板现有 Web Demo 转化为一个可持续迭代的 Godot 设计靶场。

Godot 版本采用纯前端、离线优先架构：

- 不建设登录、注册、云存档、战报和真实排行榜服务器。
- 静态配置、战斗模拟、调试工具和演示流程全部包含在 Godot 工程内。
- 存档只用于保留本机演示进度与调试选项，写入 `user://`。
- 若方案需要排行榜、周赛或玩家数据反馈，只使用固定样例或可重置的本地模拟数据。
- Web `v7.18.8` 保留为老板原型的行为证据和内容参考，不再作为需要长期维护的第二套正式产品。

## 背景依据

2026 年 7 月 13 日项目研发工作模式会议明确把当前阶段定义为“设计期”而不是“工程期”。这一阶段的首要目标是降低设计迭代摩擦，让方案能够快速被体验、比较、合并或放弃，并通过实际游玩加深对耐玩性和长期体验的理解。

因此，本工程优先服务以下活动：

1. 快速把一个设计假设做成可玩的原型。
2. 在老板原版本与调整版本之间进行明确对照。
3. 用固定随机种子、截图和简短说明复现一次体验。
4. 允许高频修改和安全回退，不让服务器兼容、账号协议或线上数据阻碍试验。
5. 每个重要提案同时产出可运行版本与简短 Markdown 说明。

原始会议逐字稿包含内部人员和组织信息，保留在用户提供的本地文件中，不提交到代码仓库；本文件只记录与工程目标直接相关的决策。

## 原型必须具备的能力

- 一键开始、重开和返回方案选择。
- 可选择“老板基线”与独立实验方案。
- 核心随机过程可注入种子，关键案例可以复现。
- 玩法数据与场景表现分离，数值调整不需要改 UI 代码。
- 能快速跳到地图、选主公、选将、战斗和结算等关键阶段。
- 可在 Windows 本地直接运行；需要分享时再增加 Web 或 Windows 导出包。
- 自动测试只覆盖高价值规则和关键演示路径，不为临时表现搭建重型框架。

## 明确不做

- 线上账号与权限系统。
- 云端数据库、云存档同步和真实排行榜。
- 为服务端接口保持长期兼容。
- 在设计尚未验证前进行大规模性能优化或生产级内容管线建设。
- 不带体验依据、只为了“功能更多”而加入的系统。

## 方案验收标准

每个设计方案至少回答四个问题：

1. 它要解决的具体体验问题是什么？
2. 玩家在可玩版本中会做出什么新的决定？
3. 与老板基线相比，体验变化能否在几分钟内被观察到？
4. 结果应当合并、继续试验还是放弃，证据是什么？

方案提交物保持轻量：可运行 Godot 版本、1 至 2 页说明、必要截图或短视频，以及对应 Git 提交。
